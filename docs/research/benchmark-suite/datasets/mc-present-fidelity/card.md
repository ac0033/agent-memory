# 数据卡：mc-present-fidelity（当下保真，K1）

> **v0.2（2026-09-14）**：30 条；构造脚本 `build/build_pf.py`，槽位由代码生成；填充与压缩由 runner 在运行时注入。全部未经人工核验。数据文件：examples.yaml（种子）+ migrated.yaml（如有）+ generated.yaml。

> 版本 0.1.0-draft（2026-09-13）｜状态：草稿，待用户审核｜结构参照 Datasheets for Datasets 的七个问题组与 Data Cards 的"事实、来源、处理、使用"分组（见 `../../public-benchmarks-survey.md` §14）。

| 项目 | 内容 |
|---|---|
| 子集名 / 前缀 | `mc-present-fidelity` / `pf` |
| 测什么 | 当前会话中的原话、数字、约束、工具报错，在隔了很多轮之后、**上下文被压缩之后**，还能不能准确复述和遵守 |
| 能力 | 主：K1 当下保真；辅：K2、K4、K12 |
| AML 叶子 | 无直接对应（最近的是 A1、A3、G5）；拟议扩展 N6"会话内保真与压缩存活" |
| 轨道 | B 行为轨（答题器回复）+ S 系统轨（压缩后记忆系统补注入了什么）；**不进 AML 问答轨**（Add/Search 无法表达"压缩"事件） |
| 种子 / 目标规模 | 4 条（本文件 `examples.yaml`）/ 120 个探针、约 40 个会话 |
| 切分 | dev 24 / test 60 / held-out 36（按会话划分） |
| 许可建议 | 数据 CC BY 4.0；填充池同为自建 CC BY 4.0 |

## 1. 动机

- **需求**：R12"当下全记得"（框架 §1）。北极星第 1 条是"手头的事全记得，上下文被压缩了也不丢"（框架 §6.1）。
- **现状**：Claude Code、Codex 都会自动压缩上下文（框架 §4）。agent-memory 没有压缩前抢救（P05），也没有事件边界打包（P06），框架 §8 把 K1 初评为 L2。
- **公开评测的空白**：LongMemEval、LoCoMo、BEAM 测的都是"跨会话被问到时能否取回"；MemoryAgentBench 按块增量喂入，但没有"压缩"这一步。没有公开集测"同一会话里、压缩之后"的保真（见 `../../gap-analysis.md` §3 G1）。

## 2. 能力映射

| 用例类型 | 主能力 | 相关机制（用于消融） | 目标比例 |
|---|---|---|---|
| `verbatim_detail`：标识符、数字、路径的逐字复述 | K1 | P04 回读、P05 抢救 | 30% |
| `constraint_survival`：早期约束在压缩后仍被遵守 | K1、K2 | P05、P06、P08 | 30% |
| `tool_output_fidelity`：工具报错或输出的逐字引用 | K1、K12 | P01、P04 | 20% |
| `file_change_recall`：本会话改过哪些文件、怎么改的 | K1 | P06 | 10% |
| `unanswerable_detail`：问一个会话里从未出现过的细节 | K1、K12 | —（测"不编造"） | 10% |

## 3. 任务格式

统一 schema 见 `../../suite-design.md` §4。本子集用到的扩展字段如下：

| 字段 | 含义 |
|---|---|
| `history.sessions[].events[]` | `filler`（harness 注入 n_turns 轮无关对话，来自填充池 `pool`）、`compaction`（固定压缩器 `compactor`）。同一个 `after_message` 位置上，事件先于探针发生 |
| `probes[].at.session/after_message` | 探针发生在会话内部，不开新会话 |
| `gold.labels.detail_kinds` | identifier / number / constraint / tool_output / file_change |
| `gold.labels.after_compaction` | 这个探针是否发生在压缩之后。每条用例都有一个"不压缩"的配对运行，用来计算存活率 |
| `gold.labels.verbatim_required` | 需要逐字一致（允许空白和全半角归一化） |
| `gold.labels.answerable` | false 表示正确行为是说明"没有定过" |
| `gold.labels.must_inject` | S 系统轨：压缩之后，记忆系统的注入块里应当包含的要点 |

## 4. 示例

`examples.yaml` 共 4 条：pf-0001（连接串要素）、pf-0002（重构约束）、pf-0003（工具报错原文）、pf-0004（从未定过的超时）。下面完整展开两条。

**示例 A：pf-0001 `verbatim_detail`**

| 部分 | 内容 |
|---|---|
| 会话 s1（2026-09-08 14:00） | 用户："报表服务今天切到 PostgreSQL 只读副本：地址 ro-2.db.example.internal，端口 54329，库名 rpt_2026，账号 report_ro；密码走环境变量 RPT_RO_PASS，别写进代码。" 助手复述确认；随后用户询问连接池配置，助手给出 pool_size=5 等 |
| 事件 | 第 3 条消息后注入 40 轮无关调试对话，然后执行一次宿主式压缩 |
| 探针 q1 | "把刚才定的只读副本连接串按 SQLAlchemy URL 格式写出来，密码用环境变量占位。" |
| 标准答案 | `postgresql://report_ro:${RPT_RO_PASS}@ro-2.db.example.internal:54329/rpt_2026` |
| 要点（5 个） | 主机、端口 54329（不是 5432）、库名、账号、密码用环境变量占位 |
| 陷阱 | 端口写成 5432；编造密码明文 |

**示例 B：pf-0004 `unanswerable_detail`**

| 部分 | 内容 |
|---|---|
| 会话 s1 | 用户定了"重试 3 次、指数退避、初始 0.5 秒""连接池用默认值"，**没有定超时** |
| 事件 | 30 轮填充 + 一次压缩 |
| 探针 q1 | "我们刚才定的请求超时是几秒来着？" |
| 标准答案 | 说明会话里没有定过超时，只定了重试和退避；请用户给值，或给出建议值供确认 |
| 陷阱 | 编造一个超时值（尤其是把 0.5 秒说成超时） |

## 5. 构造流程

| 步骤 | 做法 | 参照 |
|---|---|---|
| ① 槽位生成 | 端口、十六进制值、路径、错误码等由**代码**随机生成：保证唯一，且可以用字符串核对。不用 LLM 生成数值 | LongMemEval 按属性本体控制证据（§3） |
| ② 对话骨架 | 按类型模板写出"交代细节 → 确认 → 转入其他话题"的骨架；每个细节在历史中**只出现一次** | LongMemEval 的证据会话 |
| ③ LLM 扩写 | 用固定模型把骨架扩写成自然口语；必须保留槽位原样（生成后做字符串校验）。**本轮未调用任何 LLM**，种子由 agent 手写 | BEAM 的会话计划 → 扮演生成 |
| ④ 填充池 | 按主题清单（编码、运维、技术问答）自建中文填充对话；自动检查填充中不含任何槽位值或相近值。**不使用** ShareGPT、UltraChat 等许可不一的外部语料 | LongMemEval 用填充会话控制长度（但我们自建，以免许可问题） |
| ⑤ 压缩器 | 固定提示词 + 固定模型版本，模拟宿主的自动压缩；另在真实宿主上抽检（不计入正式分数） | 框架 §7.2"真实宿主只做抽检" |
| ⑥ 对抗负例 | 近似值（5432 与 54329）；两条相似报错；会话后段更新过的细节（只能报最新值）；从未出现过的细节 | LoCoMo 的对抗类问题；LongMemEval 的弃答题 |
| ⑦ 人工核验 | test 与 held-out 100% 核验；dev 抽检 20%。核验内容：细节唯一且无歧义、答案与原文一致、填充中无泄漏 | LongMemEval 人工编辑约 70% 的证据会话 |
| ⑧ 真实数据变体（可选，私有） | 从用户自己的 Claude Code / Codex 日志中定位真实的压缩事件，围绕压缩前的细节出题；先脱敏，涉及工作数据的会话不纳入，永不公开 | 框架 §7.9 第 5 条；ProAgentBench 的真实数据 + 时间切分 |

## 6. 标注指南（要点）

1. 每个要点必须能用字符串或规则核对；需要逐字一致的，标 `verbatim_required: true`。
2. 允许的归一化：空白、全角与半角、大小写（仅限主机名）。数字、十六进制、路径都不做归一化。
3. `constraint_survival` 的评判对象是"改动是否违反约束"，而不是"是否复述了约束"。
4. `unanswerable_detail` 中，只要给出了具体数值并声称"之前定过"，就判失败；给出建议值并明确标注"建议、待确认"，则判通过。

## 7. 质量控制

| 检查 | 方法 | 门槛 |
|---|---|---|
| 槽位唯一性 | 脚本检查：槽位值在历史中只出现在 evidence 位置 | 100% |
| 填充泄漏 | 脚本检查：填充池里不含槽位值，也不含编辑距离 ≤1 的近似值 | 0 命中 |
| 评委对齐 | 每个类型抽 25 条，双人标注；评委与人工的一致率 | ≥ 90%（本子集以字符串判定为主，门槛更高） |
| 标注一致性 | Cohen's κ | ≥ 0.8 |
| 污染 | 所有文件带 canary；held-out 不公开 | — |

## 8. 指标

| 指标 | 定义 | 主/辅 |
|---|---|---|
| 细节保真率 | 所有 `verbatim_detail`、`tool_output_fidelity`、`file_change_recall` 探针的要点命中率 | **主** |
| 压缩后存活率 | 压缩组的保真率 ÷ 同一用例不压缩配对组的保真率 | **主** |
| 约束违反率 | `constraint_survival` 中改动违反任一约束的比例 | 主（越低越好） |
| 编造率 | `unanswerable_detail` 中编造具体值的比例 | 辅（越低越好） |
| 注入召回率（S 系统轨） | 压缩后注入块覆盖 `must_inject` 要点的比例 | 辅 |
| 成本 | 抢救和注入的 token 数、额外延迟 | 辅（Q1） |

评委：先做确定性的字符串判定；只有约束遵守和允许改写的要点才交给 LLM 评委（与答题器异源，温度 0，输出结构化 JSON）。

## 9. 基线

| 对照组 | 设置 | 作用 |
|---|---|---|
| no-memory | 只有宿主式压缩，没有任何记忆系统 | 下限 |
| full-context | 不压缩，全部历史留在上下文里 | 上限参照 |
| naive-rag | 对本会话的原始轮次做检索（按消息切块） | 强基线：P04 式回读 |
| agent-memory-current | 当前实现（transcript_read + 工作记忆） | 被测系统 |
| oracle | 把 evidence 消息原样注入 | 答题器上限 |

## 10. 难度控制

| 旋钮 | 档位 |
|---|---|
| 距离（细节到探针之间的轮数） | 20 / 60 / 150 |
| 压缩次数 | 0（配对组）/ 1 / 2 |
| 每条用例的细节数 | 1 / 3 / 6 |
| 近似干扰 | 无 / 有 |

## 12. 已知局限

- 模拟压缩器不等于真实宿主的压缩策略，真实宿主只做抽检。
- 行为轨测的是"答题器 + 记忆系统"的组合。要把功劳归到记忆系统，需要借助 S 系统轨和消融（`../../suite-design.md` §7）。
- v0.1 只有中文；也还没有覆盖多模态（截图、图片）。

## v0.3 修订（2026-09-15，修订：Claude）

- **原因**：v0.2 正式运行里两版都是 100%，测不出差异。冒烟又发现两层原因：细节少时 250 字的压缩摘要能全部装下；填充对话是通用问答，压缩器一句"其余为通用问答"带过，250 字全留给了配置。
- **新增 16 条**（pf-0031 起）：会话开头交代一整块 22 项取值（生产 / 测试两套环境，含近似值），之后三段"工作型"填充（各有自己的端口、工单、文件等取值，范围与金标错开）、三次压缩；距离 48–72 轮。
  - `dense_detail`（6）：问开头那块里的 3 项；
  - `updated_detail`（6）：其中一项中途改过，问改后的值和另一项；
  - `mid_session_detail`（4）：另一组细节在第一次压缩之后才交代。
- **执行器**：再次压缩时带上上一份摘要（与真实宿主一致）；填充事件按 `pool` 取材（`work-zh-detailed` 为工作型填充）。
- **评委口径**：为说明而写的示意代码、变量名、配置键名不算编造。
- **冒烟**（3 条）：v0.2 3/3，基线 1/3（基线丢了部署地域、把填充里的缓存前缀当成记录）。更长的距离（150–210 轮）会让被测系统的工作记忆整理调用成倍增加，每条约 ¥1，所以定在 48–72 轮。
