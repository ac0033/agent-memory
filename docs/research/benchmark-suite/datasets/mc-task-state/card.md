> 版本 0.1.0-draft（2026-09-13）｜状态：草稿，待用户审核｜卡片结构同 `../mc-present-fidelity/card.md`。

| 项目 | 内容 |
|---|---|
| 子集名 / 前缀 | `mc-task-state` / `ts` |

## 1. 动机

- **需求**：R13"专注当前任务并及时更新"、R7"认知负荷低"。框架 §7.6 专项三要求在压缩、切换、跨会话、状态刚变化、并行任务几种情形下逐字段比对状态。
- **公开评测的空白**：
  - MemoryArena 和 EvoMemBench 的 in-episode 执行类任务测的是"任务最终是否成功"，不直接测状态的准确度；
  - LongMemEval-V2 的"dynamic state tracking"跟踪的是**环境**状态，不是 agent 自己的任务状态；
  - 没有公开集覆盖"被打断后恢复"和"同一项目里并行多个任务"（`../../gap-analysis.md` G2）。
- **与 agent-memory 的关系**：工作记忆已从"每个 scope 一份"改为按任务划分（框架 §2.1〔已定〕），需要用本子集验证状态是否会串。

## 2. 类型与比例

| 类型 | 场景 | 比例 |
|---|---|---|
| `state_after_update` | 决策、约束、变量中途改变，探针问当前状态和理由 | 25% |
| `interrupt_resume` | 任务中途插入 5–50 轮无关问答，然后回到任务 | 20% |
| `task_switch_return` | 切到另一个任务做了一段，再切回来 | 15% |
| `cross_session_resume` | 会话结束，第二天在新会话里续做 | 25% |
| `parallel_tasks_isolation` | 同一项目里交错推进 2–3 个任务，探针只问其中一个 | 15% |

## 3. 任务格式

| 字段 | 含义 |
|---|---|
| `messages[].task_id` | 这条消息属于哪个任务（并行和切换场景需要），不发给被测系统 |
| `probes[].kind: state_query` | 状态探针 |
| `gold.labels.state` | 六个字段：`goal`、`constraints[]`、`done[]`、`next_steps[]`、`open_questions[]`、`key_vars{}` |
| `gold.labels.stale_items` | 已经过时、不应再作为现状报出的内容 |
| `gold.labels.contamination_items` | 属于其他任务、不应混入的内容 |

## 5. 构造流程

| 步骤 | 做法 | 参照 |
|---|---|---|
| ① 操作序列 | 每个场景写成一串结构化操作：`set_goal`、`add_constraint`、`plan`、`complete_step`、`change_decision(reason)`、`add_open_question`、`resolve_question`、`switch_task`、`interrupt`、`end_session` | LoCoMo 的时间事件图；BEAM 的会话计划 |
| ② **程序化金标** | 用重放器按操作序列计算任意时刻的六字段状态，得到确定性的金标，避免人工总结出错 | 同上 |
| ③ LLM 口语化 | 把每个操作扩写成自然对话；再做回译检查：让另一个模型从对话还原操作，还原不一致的丢弃 | LongMemEval 生成后大量人工过滤（约 5% 的成品率） |
| ④ 干扰 | 打断时插入无关问答（来自自建池）；并行任务之间刻意共用词汇 | LoCoMo 的对抗类 |
| ⑤ 人工核验 | test 与 held-out 100% 核验：金标状态是否符合常识，有没有歧义 | — |
| ⑥ 真实数据变体（可选，私有） | 从用户的真实会话中截取任务片段，用 LLM 预标注状态，再由用户抽检（框架 §7.9） | ProAgentBench 的真实数据 |

## 6. 标注指南（要点）

1. `done` 和 `next_steps` 按条目匹配，允许改写，但不能合并两个条目，也不能拆开一个条目。
2. `goal` 按语义判定；`key_vars` 按键值精确匹配（数字不做归一化）。
3. 报出 `stale_items` 中的任何一项、并把它当作现状，就记一次"过时残留"。只作为历史提到（例如"原来是 5 万，后改为 3 万"）不算。
4. 报出 `contamination_items` 中的任何一项，就记一次"串线"。

## 7. 质量控制

| 检查 | 方法 | 门槛 |
|---|---|---|
| 金标可重放 | 重放器输出与卡片金标逐字段一致 | 100% |
| 回译一致 | 从对话还原出的操作序列与原序列一致 | 不一致的全部丢弃 |
| 评委对齐 | 每类抽 20 条双人标注，按字段比较一致率 | ≥ 85% |
| 标注一致性 | 按字段计算 Krippendorff's α | ≥ 0.75 |

## 8. 指标

| 指标 | 定义 | 主/辅 |
|---|---|---|
| 状态准确率 | 六个字段 F1 的平均值（列表字段按集合算 F1，字符串字段按 0/1 判定） | **主** |
| 过时残留率 | 报出过时条目的探针占比 | 主（越低越好） |
| 串线率 | 并行、切换类中混入其他任务条目的探针占比 | 主（越低越好） |
| 恢复正确率 | 打断、切换、跨会话三类的状态准确率 | 辅 |
| 更新延迟（S 系统轨） | 状态变化后，工作记忆快照在第几轮反映出变化 | 辅 |
| 状态负载 | 工作记忆快照的 token 数（被无关内容占满的程度） | 辅（Q1） |

## 9. 基线

no-memory（跨会话时什么都没有；会话内只靠上下文）/ full-context / naive-rag（在原始轮次上检索）/ agent-memory-current（工作记忆 + 会话开头注入）/ oracle（注入金标状态，作为答题器上限）。

## 10. 难度控制

操作数 6 / 12 / 24；状态更新次数 0 / 1 / 3；并行任务数 1 / 2 / 3；打断长度 5 / 20 / 50 轮；间隔会话数 0 / 1 / 3。结果按档位分桶报告。

## 12. 已知局限

- 字段边界本身有模糊之处（"约束"与"决策"），需要标注指南配合评委校准。
- 没有工作记忆读取接口的系统只能跑 B 行为轨。
- 程序化金标依赖操作序列，真实对话中"隐性状态变化"的覆盖有限，要靠真实数据变体补充。

## v0.3 修订（2026-09-15）

- **串线判定口径**：v0.2 正式运行里两版的串线率都接近 100%——被评对象（尤其是优化版的工作记忆）在单独标明的"其他并行任务"分区里列出另一个任务，评委也判为串线。v0.3 起，只有把串线条目写进目标任务的字段，或在回答里把其他任务的进度说成目标任务的进度，才算串线。
- 本子集的状态准确率不在天花板（72–89%），两版差异小是机制本身的结果，不是用例太容易，所以没有加难。
