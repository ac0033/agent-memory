## 1. 结论先行

**一句话**：v0.2 在它针对的能力上有显著、并且能归因到具体机制的提升；它没改到的地方（任务状态）没有提升；新机制带来一处回退和一处误导性提示，已查明原因。对照组、用例体检（oracle）与评委一致性因评委额度耗尽未完成，本报告只给出两版之间的配对比较与消融。

**1. 显著提升**（test 切分，同一用例上逐题配对，McNemar 精确检验）

| 能力 | 结果（优化版 vs 基线） | 对应机制与归因 |
|---|---|---|
| K5 时间与变化 | at 逐题 21/23 vs 8/23（+57 个百分点，95% CI [+30, +78]，p=0.001）；准确率 95% vs 51%；按"当时记录"提问的题 100% vs 0%，追溯更正题 100% vs 60% | P19 双时态（生效时间、记录时间、变更史） |
| K8 系统层主动浮现 | pr（S 模式）逐题 26/32 vs 13/32（+41，[+22, +59]，p=0.001）；F0.5 80%（精确率 76%，召回 100%），类比与间接线索全部召回 | P24–P26。**消融**：关掉主动浮现后退回 13/32（p=0.001），提升确实来自这一机制 |
| K9 回溯补全 | ca（E 模式）补全成功率 83% vs 17%；逐题 24/29 vs 12/29（+41，[+21, +62]，p=0.002） | P03 原文可检索、P23 原文回退、P27 完整度自评。**消融**：关掉原文工具与确认队列后补全成功率 50%、逐题 20/29（p=0.29，方向一致）；剩下的补全来自检索时自动附带的原文 |

| K13 跨宿主注入 | xa（S 模式）逐题 8/12 vs 0/12（p=0.008，n<20） | 宿主中立的 surface 与会话元数据 |

**2. 方向为正、但不显著**：K8 端到端（pr，E 模式）16/32 vs 13/32（p=0.25）；K10 确认 F0.5 54% vs 45%，无人值守正确入队 40% vs 0%；投毒鲁棒准确率 95% vs 85%（误拦 10% vs 30%，两版攻击成功率都是 0）；K13 端到端 10/12 vs 8/12。

**3. 没有提升**：K2 任务状态——ts 端到端 8/15 vs 9/15，S 模式状态准确率 72% vs 79%（过时残留 0% vs 13%）。按任务划分的工作记忆与服务端整理（P07/P08）没有带来可测的好处；而且这组用例的串线指标有测量缺陷（§8）。K1 当下保真（pf）与 K3 细节保留（ca 问答）两版都是 100%：这批用例对当前模型太容易，没有区分度。

**4. 新机制带来的问题**（详见 §7 案例）
- **回退**（at-0026）：P15 来源类型把"用户转述的法务答复"判为第三方来源，置信度被强制压成 low，事实进了复核队列而没有入库，优化版答"无法确定"，基线答对。已用缓存重放复现。
- **误导性提示**（fg-0002 等）："追溯更正"提示只看"生效日早于记录日"就触发，季度 OKR 这类普通事实也会带上它，答题器于是复述出并不存在的"之前是旧说法"。
- **成本护栏**：不需要回溯的用例上，答题器主动调原文工具 2/8（基线 0/8）；算上检索自动附带的原文是 5/8，自动附带会增加 token 开销。
- **端到端负例**：两版答题器都常顺带说出检索到的无关记忆（负例误插话 11/13 vs 13/13），v0.2 新增的"核对记录"类规范没有解决这个问题。

**5. 修复（v0.2.1，在正式运行之后做的，效果尚未测量）**：蒸馏规范写明"用户转述知情方的明确答复算 user 来源"；"追溯更正"提示只在条目确有被取代的旧版本时出现。两处都有单元测试，额度恢复后补测 at、fg 子集。

**6. 对评测集本身的判断**：差异出现的位置与各机制的针对面一一吻合，两项消融都给出了与机制对应的变化，说明套件在 K5、K8（系统层）、K9、K12、K13 上能测出真实差异。薄弱处：pf 与 ca 问答没有区分度；ts 串线指标需要改判定方式；pr 端到端负例接近地板（答题器口风松，个别金标偏严）；oracle 体检与评委一致性尚未完成。

| 项目 | 做法 |
|---|---|
| 被测对象 | 同一套答题器、评委、top_k（5）、注入字符预算（2000），只换 agent-memory 的代码版本；两版的接入规范各自取自本版本的 SKILL.md |

| 模式 | S：被测系统自己决定注入什么（不经答题器）；E：答题器按接入规范自己决定何时检索、提及什么；Q：问答 |
| 判定 | 确定性优先：遗忘硬标记与软标记、投毒特征串、先斩后奏的工具顺序、保留片段都用字符串或轨迹判定；其余由评委按固定提示词输出结构化 JSON（提示词 sha256 记在 meta.json） |
| 统计 | 比例 + Wilson 95% 区间；与 am_base 逐题配对，McNemar 精确检验 + 配对 bootstrap 区间；n < 20 标注"只看方向" |
| 消融 | 在优化版上只关一个机制重跑对应子集：关掉主动浮现（pr，S+E）；关掉原文检索、原文读取与待确认队列（ca，E） |
| 有效性核查 | 基线的内部 LLM 在本次运行里正常产出（蒸馏输出结构正确），基线低分不是记忆库为空造成的；优化版的主动浮现会吞掉 LLM 故障，所以运行期间两端都有余额与报错监控，本报告的 569 个任务全部没有报错 |

## 7. 典型成败案例

**案例一：类比迁移（pr-0006，S 模式，优化版独赢）。** 用户在问 word2vec 负采样为什么用 3/4 次方，记忆里有三天前学的 GloVe 权重函数（α=3/4，x_max=100）。优化版的副手浮现了这条记忆，并写明关联理由——两者都出于压低高频词或高频共现对影响的设计思路——还提示"仅要点，原文在 eval/s1 第 1–2 行"。基线没有系统层浮现机制。类比迁移 5 条里，优化版在 S 模式召回全部 4 条正例（pr-0006、0021、0023 等），这正是框架 §7.4 所说的"注入不等于联想"：相似度检索找得到这条记忆，把"原理相通"点明要靠副手这一步。

**案例二：追溯更正与"当时的记录"（at-0002，优化版独赢）。** 8/3 用户说站会每周一 10:00；9/10 更正"其实从 8/31 那周起就改到每周二 9:30"。问"按 9/5 那天我们手上的记录，站会是什么时间"，金标是"周一 10:00（当时还没收到更正）"。基线答成更正后的"周二 9:30"；优化版的对账把旧版本折进变更史，能区分"当时的记录"和"事后更正的事实"。按记录时间提问的题，优化版 100%，基线 0%。

**案例三：回溯补全（ca-0017，E 模式，优化版独赢）。** 记忆里只有代码评审清单的要点，完整规则在原文会话里。优化版在 memory_search 的结果里拿到自动附带的原文证据，逐条核对出 SQL 拼接、日志里的手机号、host 硬编码、函数超过 50 行四个问题，没有编造规则。基线没有回溯原文，只请用户确认目标与范围，没有复述具体约束与验收标准。

**案例四：间接遗忘（fg-0002）。** 8/12 用户私下提到在和 Northwind Labs 聊换工作，同一句话里还有本季度 OKR；8/30 要求"把那句私下的话彻底忘掉，OKR 留着"。之后请助手写季度小结：基线的检索结果里仍有被要求删除的内容，回答也带出了相关信息（检索层与回答层都判为泄漏）；优化版删除了那段记忆、擦除了原文片段，小结只围绕 OKR，保留项也没有误删。
但同一用例里优化版回答 OKR 问题时，附上了"2026-08-12 之前的记录里还是旧说法，现以更正后的为准"——这里并没有任何更正。原因是"追溯更正"提示只看"生效日（季度初 7/1）早于记录日（8/12）"就触发。已在 v0.2.1 改为只在条目确有被取代的旧版本时出现。

**案例五：新机制带来的回退（at-0026，基线独赢）。** 8/31 用户说"锦程五金的合同续签了吗？我这边还不知道，等法务消息"；9/7 用户说"法务回复了：合同其实 8 月 28 日就续签好了，有效期到 2027-08-27"。问续签实际是哪天、我们哪天知道的。基线答对；优化版答"检索到的记忆为空，无法确定"。用缓存重放优化版的写路径可以看到：蒸馏把 9/7 这条正确地整理成了记忆（生效日、有效期都对），但标成 `source_type: third_party`，P15 规则把它的置信度强制压成 low，评价门据此把它送进复核队列，正式库里什么也没有。P15 的本意是防止网上传言、粘贴材料自动变成"用户事实"，却误伤了用户转述的知情方答复。v0.2.1 在蒸馏规范里把这种情况明确归为用户来源。

**案例六：端到端负例的地板效应（pr-0014 等）。** 用户请助手给市场部王芳写邀约邮件，检索结果里有一条无关记忆"支付模块的代码评审人是后端组的王芳"。两版的答题器都在草稿之外提了这条（其中一次只是提醒"可能重名"），都被评委判为"不应浮现却浮现"。E 模式下负例的误插话两版分别是 11/13 与 13/13：这一方面说明接入规范要写明"检索到的记忆只在与当前请求相关时提及"，另一方面个别金标（只提醒重名也算浮现）偏严，已在核验台标出供复核。


## 8. 局限与诚实披露

1. **没有对照组**：no_memory、full_context、naive_rag、oracle 与"基线每轮都检索"都没跑完，所以本报告只能说"优化版比基线好多少"，不能说"比朴素 RAG 或全文上下文好多少"，也不能按框架 §6.2 判定 L2（需要显著优于朴素 RAG）。中期报告里的对照组用的是另一个答题器模型，不能合并。
2. **没有评委一致性与 oracle 体检**：评委判定的可靠性只有冒烟期的抽查；两版都没通过的 49 个任务已在核验台标出，等 oracle 跑完再判断是用例问题还是能力问题。
3. **样本量**：test 切分每个子集 12–32 条，区间较宽；每个设置只跑 1 个种子，未估计种子方差。
4. **测量缺陷**：ts 的串线判定由评委看被评对象里是否出现其他任务的词，而优化版的工作记忆按设计会单列"其他并行任务"，基线则把两件事混在一起，两版串线率都接近 100%，这个指标暂不可用；应改为只评目标任务那一份状态，或在评委提示词里说明分区列出不算串线。
5. **没有区分度的子集**：pf（当下保真）与 ca 问答两版都是 100%，需要更难的用例（更长的距离、真实压缩、更多细节）。
6. **人工核验**：用户对全部 317 条整体签核，没有逐条记录；用例由构造脚本生成，外部效度有限（合成数据）。
7. **轻微的 test 泄漏**：优化版的"追溯更正"提示是看到 test 用例 at-0017 失败后加的；而它的触发条件过宽，正是 §7 案例四的误导来源。
8. **测后修复未测量**：§1 第 5 条的两处修复（v0.2.1）在正式运行之后才做，本报告的数字不包含它们的效果。
9. **成本未度量**：优化版的主动浮现每轮多 2 次 LLM 调用，检索时自动附带原文也增加 token；本轮没有系统测量延迟与 token（Q1）。
