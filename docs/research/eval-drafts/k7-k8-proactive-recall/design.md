# 专项一：主动联想与线索唤起（K7、K8，兼顾 K6）设计说明

> 状态：v0.1 草稿，待用户审核。依据：框架文档 §5.1（K7、K8）、§7.4；需求 R5、R6、R8。

## 1. 要测什么

| 能力 | 期望行为 |
|---|---|
| K8 主动回忆时机 | 用户没有问到记忆时，也能在正确的时刻让相关记忆浮现；与当前任务无关时保持沉默。主指标 F0.5（精确率优先，〔已定〕） |
| K7 线索唤起与完整重建 | 线索和原文字面对不上时（同义、情境相似、换了称呼）也能唤起；唤起的是**完整**的情节，包括关键细节、前因后果、当时的约束 |
| K6 关联（兼顾） | 把唤起的记忆和当前任务联系起来，说明它为什么相关 |

**为什么现有的 layer3 替代不了本专项**〔实测〕：`e2e_eval.py` 判的是"检索出来的上下文块里有没有那两条事实"，并不看 agent 最后有没有主动把关联说出来。而且 layer3 的提问本身就带着提示（例如"有什么需要注意的"）。所以 layer3 的 91.67% 说明的是"两条记忆都被检索到了"，说明不了"会主动联想"。本专项的触发消息**不包含任何记忆相关的提问**，并且有负例。

## 2. 用例设置

- **历史**（`sessions`）：若干条带日期的会话，以及对应的长期记忆。
- **触发**（`trigger`）：后面的某次对话里，用户在做另一件事，**没有问到任何记忆**。
- **标准答案**（`gold`）：
  - `should_surface`：应不应该有记忆浮现；
  - `target_memory_ids`：应该浮现哪几条记忆；
  - `key_details`：浮现时必须覆盖的关键细节，用来算唤起完整度；
  - `stale_details`：时间陷阱中已经过时的说法，不能当作现状浮现；
  - `max_turn`：最晚第几轮之前要浮现，种子用例都是单轮触发，取 1。

## 3. 类型与比例（种子 12 条，比例为 2 : 1 : 2 : 1）

| 类型 | 条数 | 说明 |
|---|---|---|
| `should_surface` 应联想 | 4 | 学习、运维、数据、踩坑四个场景 |
| `indirect_cue` 线索间接 | 2 | 触发消息和记忆原文没有共同的关键实体字面 |
| `should_not_surface` 不应联想 | 4 | 字面相似或共用关键词，但和当前任务无关 |
| `time_trap` 时间陷阱 | 2 | 相关记忆有新旧两版，只能浮现最新的状态 |

## 4. 两种模式

### S 模式：系统级，只测记忆系统本身

- 把触发消息（和可选的工作记忆）交给被测系统的"浮现接口"，记录它注入的块，可以为空。
- 评委判断：有没有浮现、浮现的内容是否相关、有没有浮现过时内容、关键细节覆盖了多少。
- 各对照组的"浮现接口"：
  - **naive-rag**：每轮用触发消息检索 top-k，**无条件注入**。
  - **naive-rag+阈值**：只有相似度超过阈值才注入，阈值在不重叠的调参集上确定。
  - **agent-memory-current**：没有主动浮现机制，相当于永远不注入（这一点本身就是需要记录的基线结果）。可以另加一个参照：用 `memory_context(query=触发消息)` 近似"每轮检索"。
  - **未来的机制**（P24 线索匹配浮现、P26 记忆副手）：直接用各自的接口。

### E 模式：端到端，看答题器的最终回复

- 固定答题器，在各对照组的记忆系统下回复触发消息。agent-memory-current 组可以调用 `memory_search`，并遵循 SKILL.md。
- 评委判断：回复中有没有主动把相关记忆关联进来，内容是否正确、完整、没有过时；负例中有没有多嘴。

## 5. 指标

| 指标 | 定义 |
|---|---|
| 浮现精确率 P | 正确浮现的次数 / 全部浮现的次数（负例里的浮现都算错误） |
| 主动召回率 R | 正确浮现的次数 / 正例数（应联想、线索间接、时间陷阱三类） |
| **F0.5（主指标）** | 1.25·P·R / (0.25·P + R) |
| 过时浮现率 | 时间陷阱类中，把 `stale_details` 当作现状浮现的比例 |
| 唤起完整度 | 正确浮现的情况下，`key_details` 被覆盖的比例（取平均） |
| 线索间接召回率 | `indirect_cue` 类单独计算的 R |
| 首次浮现轮次 | 多轮用例使用；种子用例都是单轮 |
| 打扰感 | 评委打 1–5 分，重点看负例；人工抽查 |
| 成本 | 每轮注入的 token 数、检索延迟 |

## 6. 评委输出结构

```json
{
  "surfaced": true,
  "relevant": true,
  "stale": false,
  "key_details_covered": [true, false],
  "intrusiveness": 1,
  "reason": "一句话依据"
}
```

## 7. runner 需求（与专项二共用 `behavior_eval.py`，属于 D6，按 README §1 流程产出）

1. S 模式：每条用例用独立的临时库灌入数据，然后调用被测系统的浮现接口，取回注入块，交给评委。
2. E 模式：固定答题器 + 被测记忆系统，输出最终回复，交给评委。
3. 按上面的指标汇总，与各基线做配对统计。

## 8. dry-run 发现（2026-09-13，不调 LLM）

朴素 RAG 在各触发消息上的最高余弦（bge-m3）如下：

| 用例类型 | 用例 | 最高余弦 |
|---|---|---|
| 正例（应联想、线索间接、时间陷阱） | pr-01～06、11、12 | 0.519–0.726 |
| 负例（不应联想） | pr-07～10 | 0.493–0.669 |

两组区间**大面积重叠**。以阈值 0.6 为例：三个负例（pr-07、09、10）会被误注入，同时漏掉 pr-01、pr-02 两个正例。

结论：只凭相似度阈值无法判断"该不该主动联想"，需要一个相关性判断环节，例如机制 P26 记忆副手。这条可作为专项一的基线证据，但需要在扩充后的用例上复验。

## 9. 已知局限

- 种子 12 条只能验证评测能跑通；审核后要扩到 30 条以上（负例的比例保持在 1/3 左右），并补充真实数据用例。
- 单轮触发测不出"第几轮才想起来"，需要补多轮用例。
- "打扰感"的主观性比较强，需要人工抽查来校准评委。
