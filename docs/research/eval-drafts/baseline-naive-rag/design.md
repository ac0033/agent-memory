# 朴素 RAG 基线设计说明（所有专项共用）

> 状态：v0.1 草稿，待用户审核。依据：框架文档 §6.2（L2 的判定需要显著优于朴素 RAG）、§7.2 原则 3。

## 1. 为什么必须有这个基线

AML 首期开源榜的前三名分别是朴素 RAG、迭代 BM25，以及"逐字带时间戳的轮次 + 原子事实"。LongMemEval-V2 里，"coding agent 直接查原始轨迹"的 72.5% 也高于"在提炼笔记上做 RAG"的 48.5%。结论是：**如果 agent-memory 的蒸馏、对账、整理等复杂机制在某项能力上赢不了"对原文做简单检索"，那这些机制在这项能力上就缺乏依据。**

## 2. 定义

| 项目 | 设定 |
|---|---|
| 语料 | 历史会话的**原始轮次**，也就是用例里的 `sessions.turns`。不做蒸馏、不做对账、不做整理 |
| 切块 | 一条消息一个块，保留 `session_id`、`date`、`role` 三项元数据 |
| 检索 | 与 agent-memory 用同一个嵌入器（bge-m3）。分两个变体：`naive-rag-dense`（纯稠密检索）和 `naive-rag-hybrid`（稠密 + BM25，用 RRF 融合）。返回 top-k，k=5 |
| 渲染 | 按时间先后列出命中的块，每块标注日期和会话；与 agent-memory 的注入块使用相同的 token 上限 |
| 时间 | 不做任何时态处理，新旧说法都可能被检索到。这正好用来检验"时间陷阱"类用例 |

## 3. 在各专项中怎么用

| 专项 | S 模式 | E 模式 |
|---|---|---|
| 专项一（主动联想） | 每轮用触发消息检索，无条件注入 top-k（`naive-rag`）；另设一组"相似度超过阈值才注入"（`naive-rag+阈值`），阈值在不重叠的调参集上确定 | 答题器可以调用 `archive_search`，由它自己决定调不调 |
| 专项二（完整性对齐） | 不适用（这个专项测的是答题器的行为） | 答题器只有 `archive_search`，没有提炼后的记忆层 |
| layer1–3 | 用问题检索，交给现有的评委 | — |

## 4. 另外两个基线

- **no-memory**：空库，不注入任何内容，也不提供任何检索工具。
- **full-context**：把全部历史原文按时间顺序放进上下文，仅在放得下时才跑，是能力的上限参照。

## 5. 结果怎么读

- agent-memory 在某项能力上**显著优于** naive-rag（配对检验）：说明相关机制有贡献，可以作为 L2 及以上成熟度判定的依据。
- **与 naive-rag 持平或更差**：先检查这项能力依赖的机制，考虑是否简化，或者把"退回原文检索"（机制 P23）纳入主路径。
- **full-context 与 agent-memory 的差距**：衡量压缩和选择造成的损失；同时对比两者的 token 成本（约束 Q1）。

## 6. 实现位置

基线属于评测的一部分，代码要放在 `evals/runners/` 下，受 D6 约束。按 `../README.md` §1 的流程，获得授权后在本目录起草代码草稿，由用户迁入。
