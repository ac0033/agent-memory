## 1. 为什么有这个目录

`evals/` 下的数据集、rubric、门槛和 runner 都属于 D6 可信根，agent 不能修改。新的评测按下面的流程产出：

1. agent 在本目录起草，内容包括设计说明、种子用例，以及需要的 runner 设计；
2. 用户审核：用例是否真实、类型比例是否合理、门槛定多少，必要时直接修改；
3. **用户亲自**迁入 `evals/` 并提交 git，每次迁入记为评测契约的一个新版本；
4. runner 的代码同样属于 `evals/`：agent 只在得到授权后在本目录起草代码草稿，由用户迁入。

## 2. 目录

| 路径 | 内容 | 覆盖能力 |
|---|---|---|
| `k9-k10-completeness-alignment/` | 专项二：完整性自知与理解对齐。设计说明 + 12 条种子用例 | K9、K10 |
| `k7-k8-proactive-recall/` | 专项一：主动联想与线索唤起。设计说明 + 12 条种子用例 | K7、K8（兼顾 K6） |
| `baseline-naive-rag/` | 朴素 RAG 基线的设计说明 | 所有专项共用 |

用例都写在各自目录的 `cases.yaml` 里（多文档 YAML，文档之间用 `---` 分隔），方便一次审完。迁入时按 `id` 拆成单文件，放到 `evals/datasets/<suite>/`，这与现有 layer1–3 的做法一致。

## 3. 所有专项共用的约定

### 3.1 两种评测模式

| 模式 | 被测对象 | 看什么 | 适用 |
|---|---|---|---|
| **S 模式（系统级）** | 只测记忆系统本身，不经过答题器 | 记忆系统在某个时刻提供或注入了什么（包括什么都不注入） | 控制变量，隔离出机制本身的作用；AML 式 |
| **E 模式（端到端）** | 固定答题器 + 记忆系统 + 工具 | 答题器的回复和工具调用轨迹 | 用户真正能感知到的行为 |

两种模式的结果分开报告，不合并成一个分数。

### 3.2 固定配置（〔已定〕固定答题器）

- **答题器（actor）**：仓库内可控的 harness，比如 LangGraph 的 ReAct 或一个简单循环。固定模型版本，temperature 为 0，每条用例至少跑 3 个种子，报告均值和区间。
- **评委**：与答题器不同源（沿用 `AGENT_MEMORY_JUDGE_*` 配置），温度为 0，输出结构化 JSON。
- **缓存**：沿用 `data/logs/llm_cache/`。
- **真实宿主**（kimi、Claude、Codex）只做抽检，不进入正式分数。

### 3.3 灌库方式

- **预置记忆**（默认）：直接写入用例里的 `memories`，经过评价门和对账。这样可以把"沉淀质量"的影响排除掉，只测当前专项关心的能力。
- **真实蒸馏**（附加）：把 `sessions.turns` 走一遍完整的蒸馏管线，测端到端效果。
- 用例里的 `sessions.turns` 同时充当**原文归档**：可以回溯补全时，从这里读取。

### 3.4 基线（每个专项都要跑）

| 基线 | 说明 |
|---|---|
| no-memory | 空库，没有任何记忆和归档 |
| full-context | 把全部历史原文放进上下文（放得下时才跑） |
| naive-rag | 在原始轮次上做朴素检索，见 `baseline-naive-rag/` |
| agent-memory-current | 当前版本的 agent-memory，按 SKILL.md 的规范接入 |

公平性要求：答题器、评委、注入 token 上限都相同。

### 3.5 统计

- 按用例配对，做 McNemar 精确检验，并给出 bootstrap 95% 区间（沿用 `evals/runners/metrics.py`）。
- 样本少于 20 条时，标注"不足以下强结论"。当前两个专项各只有 12 条种子，**只能用来验证评测本身能不能跑通，不能用来下结论**。用户审核后需要扩充到 30 条以上，并补充真实数据用例。

### 3.6 主指标口径（〔已定〕精确率优先）

主动浮现和复述确认都用 **F0.5** 作为主指标：

F0.5 = 1.25 · P · R / (0.25 · P + R)

其中 P 是精确率，R 是召回率。F0.5 更看重精确率，也就是宁可少说。

### 3.7 用例字段约定（现有字段 + 新增字段）

| 字段 | 说明 | 来源 |
|---|---|---|
| `id` / `description` / `sessions[].session_id / date / turns / memories` | 与 layer1–3 相同 | 现有 |
| `memories[].confidence / last_verified` | 可选；专项二用它来构造"记错陷阱" | 新增 |
| `suite` / `type` | 所属专项和用例类型 | 新增 |
| `trigger.date / context / user_message` | 触发会话：日期、可选的场景说明、用户消息 | 新增 |
| `unattended` | 是否无人值守（此时 ask_user 工具不可用） | 新增 |
| `simulated_user_reply` | 答题器调用 ask_user 时返回的模拟回复 | 新增 |
| `expected` | 期望的行为标签（专项二） | 新增 |
| `gold` | 应不应该浮现、目标记忆、关键细节、过时细节、最晚在第几轮浮现（专项一） | 新增 |
| `rubric.essential / pitfalls` | 与现有一致：essential 必须全部覆盖，触发任一 pitfall 一票否决 | 现有 |

## 4. 需要用户审核的要点

1. 种子用例的情境是否贴近你的真实使用（合成数据，不含工作数据）；
2. 类型比例：专项一为 2 : 1 : 2 : 1，专项二每类 2 条；
3. 两种模式、四个基线是否都要跑；
4. 门槛：建议先跑基线，再根据结果定门槛，暂不预设；
5. 真实数据：是否从你自己的 Codex / Claude / kimi 会话里按时间切分来构造用例（流程见框架文档 §7.9 第 5 条）。
